<!-- @block intro -->
Какие события есть в шине, когда они приходят и с какими аргументами. Как подписываться и читать аргументы — на странице "[События](https://gitlab.com/great-war/wiki/-/tree/master/doc/plugins/api/events.md)".

<!-- @block notation -->
В колонке «Аргументы» указано, в каком виде аргумент приходит плагину (поле `type` у `GwpValue`, префикс `GWP_T_` опущен):

| Тип | Что приходит |
|---|---|
| `OBJECT` | id онлайн-объекта (в Lua это `game_object`) |
| `SERVER_OBJECT` | id серверного объекта ALife (в Lua `se_stalker`, `se_actor`, `sim_squad_scripted`, `se_smart_terrain` и другие наследники `cse_abstract`) |
| `NUMBER` | число `double`. Все числа из Lua приходят так, даже id и коды клавиш: читайте целые через `gwp::EventView::integer()` |
| `STRING` | строка |
| `BOOL` | логическое |
| `VEC3` | вектор (в Lua `vector`) |
| `LUA_REF` | Lua-таблица или userdata без нативной формы; содержимое плагину недоступно |
| `NIL` | пусто |

Нумерация аргументов — с нуля, как индекс в `argv` и в методах `gwp::EventView`.

Схема описывает то, что получает плагин. Таблица флагов события с результатом в схему не входит и плагину аргументом не передаётся (см. "[События с результатом](#события-с-результатом)"). Схема скриптового события — значение в таблице `intercepts` в `axr_main.script`, схемы встроенных событий задаёт движок.

Схема — это договорённость, а не фильтр. С ключом запуска `-addon_debug` (или консольной командой `gw_event_schema_check 1`) движок сверяет со схемой каждую отправку события и при несовпадении один раз на событие пишет в лог предупреждение `do not match the schema`; событие при этом рассылается как есть. Поэтому тип аргумента в обработчике всё равно проверяйте (`gwp::EventView` делает это сам и возвращает значение по умолчанию при несовпадении).

<!-- @block builtin_intro -->
Эти события отправляет сам движок из C++. Они объявлены движком, работают без Lua-скриптов, и на них можно подписаться как из плагина, так и из Lua обычным `RegisterScriptCallback`.

<!-- @block builtin_outro -->
У встроенных событий нет результата (`event->result == NULL`).

Ещё четыре события движок объявляет не в `kBuiltinNames`, а лениво, при первой надобности (в таблицу выше генератор их не берёт); подписаться можно и раньше, прямо в `on_init`: шина запоминает имя.

<!-- @block sequence -->
Порядок событий по коду движка. Порядок подписчиков **внутри** одного события не гарантируется.

**Загрузка сейва** из главного меню (уровень не загружен) или загрузка сейва другого уровня:

1. `level_on_stop`, `actor_on_destroy`, `alife_on_end` — если до этого был загружен уровень.
2. `engine_on_script_start` — Lua перезапущен (без ключа `-keep_lua`).
3. Lua-`on_game_start` всех скриптов: Lua-скрипты подписываются на события.
4. `alife_on_start` с причиной `"load"`. Данные плагинов, persistent-значения шины данных и таймеры уже очищены, из сейва ещё ничего не прочитано.
5. Движок читает из сейва данные плагинов, persistent-значения шины данных и таймеры (без `data_on_changed`).
6. Lua-событие `load_state` (если у сейва есть файл `.scoc`): persistent-значения шины данных уже видны через `data_bus.get`.
7. `alife_on_load` — данные плагина доступны через `save_read`, persistent-значения — через `data_get` / `data_bus.get`.
8. Lua-события регистрации объектов: `se_actor_on_register`, `squad_on_register` и т.п.
9. `alife_on_after_load`.
10. Спавн объектов уровня, среди них `actor_on_spawn` (Lua-событие `on_game_load` отправляет биндер актора при его спавне, раньше `actor_on_spawn`).
11. `level_on_start`.
12. `level_on_frame` каждый кадр.

**Загрузка сейва того же уровня** (из игры, уровень сейва совпадает с текущим): уровень не перезагружается, пересоздаётся только ALife.

1. Доставка пачек подписок `GWP_SUBSCRIBE_BATCH` без учёта `throttle_ms`, пока id объектов ещё действительны.
2. `actor_on_destroy` — клиентские объекты уровня удаляются.
3. `alife_on_end` — ALife пересоздаётся.
4. Шаги 2–10 «загрузки сейва»: `engine_on_script_start`, Lua-`on_game_start`, `alife_on_start` с причиной `"load"`, чтение данных сейва, `load_state`, `alife_on_load`, регистрация объектов, `alife_on_after_load`, спавн объектов и `actor_on_spawn`.
5. `level_on_frame` каждый кадр.

`level_on_stop` и `level_on_start` здесь **не приходят**: уровень не останавливается. Действия «после каждой загрузки», которым нужен актор или игровое время сейва (например, запуск таймеров игрового времени), делайте в `actor_on_spawn`: оно приходит и здесь.

**Новая игра:**

1. `level_on_stop`, `actor_on_destroy`, `alife_on_end` — если до этого был загружен уровень.
2. `engine_on_script_start` — Lua перезапущен (без ключа `-keep_lua`).
3. Lua-`on_game_start` всех скриптов.
4. `alife_on_start` с причиной `"new_game"`. Данные плагинов, persistent-значения шины данных прошлой игры (без `data_on_changed`) и таймеры очищены; обычные значения шины остаются.
5. Движок создаёт объекты новой игры; Lua-события регистрации объектов (`se_actor_on_register`, `squad_on_register` и т.п.).
6. Спавн объектов уровня, среди них `actor_on_spawn`.
7. `level_on_start`.
8. `level_on_frame` каждый кадр.

Сейва нет: `load_state`, `alife_on_load` и `alife_on_after_load` не приходят, а `save_read` возвращает `GWP_ERROR`.

**Сохранение:**

1. Lua-событие `save_state`.
2. `alife_on_before_save` — вызывайте `save_write`.
3. Движок записывает сейв; данные плагинов — отдельный чанк в потоке ALife.
4. `alife_on_after_save`.

**Переход на другой уровень** идёт через автосейв и загрузку этого автосейва новым ALife:

1. Автосейв по схеме «сохранение»: `save_state`, `alife_on_before_save`, `alife_on_after_save` с именем `<пользователь> - autosave.scop`.
2. `level_on_stop`, `actor_on_destroy`, `alife_on_end`.
3. Шаги 2–12 «загрузки сейва», но `alife_on_start` приходит с причиной `"level_change"`.

Поэтому данные, записанные через `save_write`, persistent-значения шины данных и persistent-таймеры переходят на новый уровень.

**Выход в главное меню** (завершение текущей игры, а не открытие меню поверх игры): `level_on_stop`, `actor_on_destroy`, `alife_on_end`.

**Выход из игры:** если уровень загружен — `level_on_stop`, `actor_on_destroy`, `alife_on_end`; затем при выгрузке плагинов — `on_unload` (см. "[Точка входа](https://gitlab.com/great-war/wiki/-/tree/master/doc/plugins/api/entry_point.md)").

<!-- @block script_intro -->
Эти события отправляют Lua-скрипты через `SendScriptCallback`. Все они объявлены в таблице `intercepts` в `axr_main.script`, там же их схемы. Скрипт, из которого событие отправляется, указан в заголовке группы.

Жизненный цикл актора (`actor_on_update`, `actor_on_first_update`, `actor_on_net_destroy` и другие) с этапа B-4 отправляет движок, раздел выше. Из `bind_stalker_ext.script` остались только события фонарика (`actor_on_torch_enabled` / `_disabled`), без аргументов.

Частые события (`actor_on_update_fast` / `_slow`, `on_key_hold`, `monster_on_update`) при подписке плагина переводят аргументы в `GwpValue` на каждом вызове. Для кадровой логики лучше встроенное `level_on_frame`. События «по объекту» (`npc_on_update`, `monster_on_update`, `squad_on_update`) удобнее получать пачкой раз в кадр, а не вызовом на каждый объект: `event_subscribe_ex` с `GWP_SUBSCRIBE_BATCH`, см. "[Подписка с опциями](https://gitlab.com/great-war/wiki/-/tree/master/doc/plugins/api/events.md#подписка-с-опциями-троттлинг-и-пачки-event_subscribe_ex)".

<!-- @block result_outro -->
Из этих событий Lua-скрипт отправляет только `actor_on_before_hit`, остальные шлёт движок. Lua передаёт результат таблицей флагов (`{ret_value = true}`), а плагин читает и меняет его через `event->result` (или `gwp::EventView::result_bool` / `set_result`); если обработчики плагинов изменили результат, в поле таблицы записывается boolean. Сама таблица флагов плагину аргументом не передаётся, если она последний аргумент (так у всех событий выше). Подробно — в разделе "[Результат события](https://gitlab.com/great-war/wiki/-/tree/master/doc/plugins/api/events.md#результат-события)".
